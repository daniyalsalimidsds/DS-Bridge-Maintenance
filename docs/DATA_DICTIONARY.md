# فرهنگ داده و قواعد پویا

## شناسنامه پل

منبع حقیقت فرم، فایل `reference/شناسنامه_فنی_پل_نشریه_367.xlsx` است. ابزار `tools/generate_bridge_schema.py` ردیف‌های ۸ تا ۲۷ شیت `01_خلاصه_پروفایل_منویی`، برچسب‌ها و Data Validationها را استخراج می‌کند. مقدارهای پرشده نمونه فقط به `example` تبدیل می‌شوند و پیش‌فرض فرم نیستند.

هر رکورد پل شامل این اجزاست:

- `id`, `name`, `code`, `use`
- `profile`: نگاشت ID ثابت فیلد به مقدار کاربر
- `profileSchemaVersion`, `profileSourceSha256`
- `location`: `lat`, `lon`, `accuracyM`, `capturedAt`, `provider`, `source`
- `createdAt`, `updatedAt`, `archived`

## انتخاب چک‌لیست

منطق محافظه‌کارانه است: دسته عمومی همیشه نمایش داده می‌شود؛ دسته مصالح یا جزء فقط وقتی شناسنامه وجود آن را نشان دهد اضافه می‌شود. اگر اطلاعات ناکامل/نامشخص باشد، دسته «کنترل کامل‌بودن شناسنامه فنی» نیز نمایش داده می‌شود.

- کاربری `راه`: روسازی، ایمنی راه، زهکشی و اجزای مرتبط.
- کاربری `راه‌آهن`: ریل، جوش، هندسه خط و ایمنی راه‌آهن؛ بالاست فقط برای روسازی بالاستی و بست مستقیم فقط برای ریل مستقیم روی عرشه.
- مصالح بتن: ترک، پوسته‌شدن، خوردگی آرماتور، دوام و خرابی ترمیم.
- مصالح فولاد: خوردگی، خستگی، جوش، پیچ/پرچ، کمانش و کاهش مقطع.
- اجزای ثبت‌شده: عرشه، تیر، خرپا، قوس، کابل، تکیه‌گاه، درز، پایه، کوله، پی، آبراهه، تأسیسات، لرزه‌ای و غیره.

کاتالوگ پایه ۱.۶.۰ شامل ۴۱ دسته و ۴۹۷ مورد است؛ ۳۲ مورد از آن در این نسخه افزوده شده است. این تعداد مستقل از تعداد موارد نهایی یک پل است؛ موارد مصالح به اجزای موجود تخصیص داده می‌شوند و فهرست به شناسنامه وابسته است.

## بازدید و آسیب

هر مورد چک‌لیست می‌تواند چند رخداد مستقل داشته باشد. هر رخداد وضعیت، شرح، GPS و تصاویر خود را دارد. `none` فقط با `assessed=true` به معنی «بررسی شد؛ این آسیب مشاهده نشد» است. ع.ا.ب با `findingType=inspection-gap` در فهرست پیگیری نگهداری می‌شود؛ آسیب مشاهده‌شده `findingType=damage` دارد.

## فیلدهای حاکمیتی افزوده در ۱.۷.۰

| مدل/فیلد | معنی |
|---|---|
| `users[].personnelId`, `qualification` | هویت پرسنلی، رشته/مدرک/سابقه/آموزش/گواهی/انقضا، انواع مجاز و مجوز inspect/QC با تأییدکننده مستقل |
| `inspections[].workflowStatus` | `draft`, `returned`, `submitted`, `approved`; فقط دو حالت اول قابل ویرایش‌اند |
| `inspectorId`, `submittedByUserId`, `fieldHash` | هویت احرازشده ارسال‌کننده و hash ثابت snapshot میدانی |
| `inspectorReassignments[]` | هویت قبلی/جدید، دلیل، مجازکننده و زمان تغییر بازرس |
| `reviews[]` | بازبین، نوع QC، تصمیم approve/return، نظر، hash بازبینی‌شده و زمان |
| `criticalFindings[]` | لینک رخداد/آسیب، کشف، اقدام فوری، محدودیت و توجیه، اعلان، مسئول/مهلت، پذیرش، رفع/مدرک و بستن مستقل |
| `inspectionVoids[]` | ابطال غیرمخرب گزارش با دلیل، تأییدکننده و زمان |
| `reportRevisions[]` | snapshot ارسالی/تأییدشده، شماره چرخه، hash و زنجیره approval/supersession |
| `inspectionPrograms[]` | فاصله و مبنا، موعد پایه/مؤثر، override ریسک و دلیل، تأخیر، آخرین و بعدی |
| `audit_events` | توالی append-only شامل actor/action/entity/reason/revision/time، predecessor hash و event hash |
| `report_registry` | نگاشت UNIQUE میان UUID بازدید و شماره نمایشی رسمی تخصیص‌یافته در QC |

## فیلدهای افزوده ۱.۶.۰

| فیلد | معنی |
|---|---|
| `checklistSchemaVersion`, `scoringVersion` | نسخه قرارداد مشاهده و روش محاسبه |
| `items[].assessed` | تأیید صریح انتخاب وضعیت |
| `items[].applicable` | کاربرد مورد در پل؛ false نیازمند دلیل در note |
| `items[].occurrenceIndex` | شماره هویت رخداد؛ پس از حذف شماره‌گذاری مجدد نمی‌شود |
| `occurrenceCounters` | بیشترین شماره مصرف‌شده هر مورد؛ شماره حذف‌شده دوباره استفاده نمی‌شود |
| `items[].scoring` | کلید امتیاز، ضریب، نوع منبع، عنوان مرجع و علت قیاس |
| `itemLocations[key]=null` | حذف صریح GPS؛ مجوز بازگرداندن مختصات قدیمی نیست |
| `internationalAssessment` | نوع پل/کالورت، نام ارزیاب و نمره/شواهد ۱۱ جزء |
| `elementAssessments` | نام عنصر، واحد، کل، مقادیر CS1–CS4 و مرجع |
| `scores` | snapshot هنگام نهایی‌سازی: نسخه، زمان، SHA منبع، جمع‌ها، پوشش و ارزیابی بین‌المللی |

در بازدید نهایی snapshot در گزارش به کار می‌رود. در سابقه قدیمی بدون snapshot، محاسبه با برچسب بازتحلیل انجام می‌شود؛ داده اصلی سابقه به‌صورت پنهانی بازنویسی نمی‌شود. سابقه دارای پیش‌فرض none و فاقد تأیید مشاهده، در پوشش بررسی‌نشده محسوب می‌شود.

وضعیت‌ها: `none`, `low`, `medium`, `emergency`, `uninspectable`. `unknown` حالت مهاجرت/اعتبارسنجی fail-safe است و ارسال رسمی را مسدود می‌کند. بررسی‌نشده همچنان با `assessed=false` متمایز است. `N` نبود جزء و `U` نامعلوم در فرم FHWA مستقل از مقیاس آسیب‌اند.

ارسال هر بازدید بدون فایل امضای همان بازدید و هویت احرازشده بازرس، یا با مقدار شدت unknown/بررسی‌نشده، در JavaScript و transaction بومی رد می‌شود. تأیید رسمی به بازبین واجدصلاحیت مستقل نیاز دارد. اقدام اصلاحی، مسئول و مستندات تعمیر بعداً در گردش کار مستقل آسیب ثبت می‌شوند و جزو فرم ثبت بازدید نیستند.
